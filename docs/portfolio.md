# Flowent · Материал для портфолио

**Задача.** Согласования расходов, доступа и командировок используют разные маршруты. Когда схема хранится отдельно от реализации, изменение порога согласования требует сверять документацию, код и уже начатые заявки.

**Вклад.** В проекте я определил границы поддерживаемого BPMN, описал требования и критерии приёмки, спроектировал модель исполнения, контракт API и проверяемые инварианты. Собрал интерфейсы для аналитика, исполнителя и оператора и автоматизировал проверку сквозных сценариев.

**Требования.** Одна опубликованная версия закрепляется за экземпляром. Ветка выбирается по типизированному условию. Соединение ждёт ветви одного запуска параллельного шлюза. Форма и права проверяются на сервере. Повтор команды возвращает сохранённый результат. Таймер переживает перезапуск.

**Архитектура.** React и bpmn-js редактируют модель. FastAPI валидирует и публикует XML вместе с исполняемым графом. PostgreSQL хранит версии, токены, задачи, задания worker, квитанции и историю. Блокировка экземпляра упорядочивает переходы, а уникальная квитанция связывает команду с результатом.

**Проверка.** В браузере изменение имени задачи прошло путь от редактора до активной задачи экземпляра. Интеграционные проверки подтвердили параллельные переходы, обработку отклонения и уточнения, таймеры, контроль SLA и восстановление после инцидента. В отдельной проверке сохранённый таймер сработал один раз после остановки worker и перезапуска API.

**Результат.** В учебной среде работают три согласования и лаборатория, связывающая реальный HTTP-ответ с состоянием экземпляра и событиями. Для интервью можно открыть диаграмму, объяснить идентификатор активации split, завершить одну ветвь и показать, почему следующая задача стала доступна только после второй.
